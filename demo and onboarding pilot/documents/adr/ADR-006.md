# ADR-006: Port Assignments for Staging and Production

## Status
Accepted (revised 2026-11-18)

## Date
2026-11-12 (revised 2026-11-18)

## Context
Staging and production both run Docker Compose with backend (port 8000) and frontend (port 8080) services. The staging instance experienced persistent port conflicts (dead `docker-proxy` processes holding ports 8000/8080 after container removal). Production runs on a private OCI instance with no port conflicts.

Staging and bastion share a single VM (`roc-dis`, `145.241.152.126`). Caddy runs on the bastion and reverse-proxies to local services on `127.0.0.1`.

## Decision
- **Staging** (`roc-dis`, `145.241.152.126`): Backend bound to `127.0.0.1:8000`, frontend bound to `127.0.0.1:80`. Not directly reachable from the public internet; Caddy on the same host reverse-proxies `stage.kfl.ke` to localhost.
- **Production** (`10.20.1.69`): Backend bound to `0.0.0.0:8000`, frontend bound to `0.0.0.0:8080`. Ports are published but the backend is not directly reachable from the public internet (Caddy on bastion proxies to `10.20.1.69:8000/8080`).
- **Bastion** (`145.241.152.126`): Caddy listens on 443 for `roc.kfl.ke` and `stage.kfl.ke`; reverse-proxies `stage.kfl.ke` → `127.0.0.1:8000/80` (local staging) and `roc.kfl.ke` → `10.20.1.69:8000/8080` (production).

## Rationale
- **Localhost binding**: Staging backend and frontend bind to `127.0.0.1` only, preventing external access to staging APIs directly. Caddy is the single entry point.
- **Production standard ports**: Production uses 8000/8080 for consistency with application defaults; Caddy handles external HTTPS on 443.
- **Caddy as single entry point**: All external traffic flows through Caddy on the bastion, which handles TLS and routing to the correct backend.
- **SSH restriction**: SSH on the shared VM is restricted to the operator's IP allowlist only.

## Consequences
- **Positive**: No port conflicts, production uses standard ports, Caddy centralizes external access, reduced SSH attack surface.
- **Negative**: Staging and bastion share a single VM; staging port/host changes require updates to `docker-compose.staging.yml`, Caddyfile, and any client configurations; staging is not directly accessible from outside the bastion.
- **Mitigation**: All port mappings are documented in deployment scripts and Caddyfile; staging is not directly accessible from outside the bastion.

## Alternatives Considered
- **Same ports on both instances**: Rejected — staging port conflicts caused repeated deployment failures.
- **Host networking**: Rejected — bridge networking with port mapping provides better isolation.
- **Separate staging host**: Rejected — shared bastion/staging VM avoids maintaining a second cloud instance.

## Review
Review if staging should move to a dedicated host without port conflicts, in which case standard ports (8000/8080) could be restored.
