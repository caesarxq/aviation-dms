First establish a controlled source-to-rule register, then implement a shared, deterministic workflow engine that enforces each manual's actors, transition conditions, evidence, timers, separation of duties, audit events and notifications at the API boundary. The source baseline is now the six user-supplied approved PDFs, not the older converted HTML/seeding alone. The first vertical slice should be **SMS occurrence reporting through assessment, investigation/follow-up and closure**. It has clear source roles, timers and close criteria. In parallel, synchronize the attachment/approval metadata and fix identity/session security before trusting actor attribution in production.

- Document versioning has explicit transitions and a KCAA publish gate, but approval provenance is not reconciled to the embedded manual evidence. Change Request status updates accept caller-supplied statuses without a complete transition map.

- DG acceptance currently uses five Boolean checks. DOC-007 requires a richer acceptance/handover sequence, including packaging/labels, signed documentation/contact details, physical inspection, quantity/weight/aircraft limits, weather confirmation, restricted access, communication and hold-on-noncompliance.

## 3. Common workflow implementation model

Create a **versioned workflow specification** for each lifecycle, linked to immutable controlled-source identifiers. Every transition definition should state:

- workflow key and specification revision;
- source document ID, exact DMS version, manual issue/revision/date, section/appendix and extracted clause text/hash;
- source status: `source-derived`, `postholder-validated`, `authority-approved` (where required), `active` or `superseded`;
- `from_state → to_state`, permitted actor role and active delegation, permission, SoD rule;
- preconditions, required evidence/fields, manual-specific checklist revision and failure response;
- timer event (start, due time, calendar/timezone, pause/exception rule) and escalation owner;
- audit event, notification/outbox event and idempotency key;
- reversal/reopen/correction policy and superseding record behavior.

Implement transition commands server-side (not arbitrary `PATCH status`) through one service boundary. Persist state change, transition evidence and audit event transactionally; deliver notifications through an outbox after commit. Reject unknown states and unconfigured sources. Keep source-derived but unvalidated rules visible in test/staging only; **fail closed for production flight-release, mandatory reporting, authority approval and return-to-service gates** when the applicable rule/source is not active.

Keep user interface status labels derived from the workflow API; the UI may explain a blocked transition but cannot authorize it. Do not use LLM output to decide approval, reportability, risk acceptance, airworthiness, or release.

## 5. Test and assurance plan

For every source-linked transition, create tests for:

1. valid next transition and correct actor;
2. invalid/skipped/backward transition;
3. unauthorized role, expired/missing delegate and actor-role mismatch;
4. proposer/reviewer/approver/investigator/verifier separation of duties;
5. missing required checklist item/evidence/source version;
6. timer boundary, timezone, late entry, retry and idempotent duplicate notification;
7. audit event and source/rule version captured on every transition;
8. concurrent competing decisions and attempted direct status mutation;
9. reopen, correction, superseded manual and retrospective rule change;
10. confidential/sensitive record visibility and export behavior;
11. regulator decision evidence absent, pending, rejected or superseded;
12. full browser path from role login to blocked/allowed transition and focused evidence display.

The acceptance artifact is a traceability table: `manual clause → workflow requirement → rule version → API command → role → evidence → test ID → audit event`. A passing page load or CRUD test does not establish manual conformance.
