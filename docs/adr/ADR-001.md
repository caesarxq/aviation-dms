# ADR-001: SQLite for Production Data Store

## Status
Accepted

## Date
2026-11-11

## Context
The Aviation DMS requires a relational data store for controlled documents, audit events, user identities, and compliance records. The system must run on a single OCI compute instance with limited operational overhead, support fail-closed deployment, and allow straightforward backup/restore of the complete `/app/data` directory as one set.

## Decision
Use SQLite (via `aiosqlite` with Python 3.11 and FastAPI) as the production data store, with the database file at `backend/data/dms.db` (or `/app/data/dms.db` in containers).

## Rationale
- **Single-instance deployment**: SQLite requires no separate database server, simplifying the OCI instance to four containers (backend, frontend, upload-validator, clamd).
- **Atomic backup/restore**: The entire `/app/data` directory (database + uploads + KCAA evidence + audit attachments) can be backed up and restored as one filesystem set, which is essential for the off-host backup/restore drill required by the Records Custodian and Accountable Manager.
- **Zero operational overhead**: No database patches, connection pooling, or replication to manage on the production instance.
- **Simplified schema migrations**: SQLite schema evolves with the application; no separate migration tooling required.
- **Adequate for scope**: The onboarding pilot and restricted production use involve a small number of concurrent users and documents, well within SQLite's operational envelope.

## Consequences
- **Positive**: Simple backup/restore, no separate DB server, low operational overhead, portable database file.
- **Negative**: Single-writer limitation (mitigated by process-local semaphore and fail-closed uploads), no horizontal scaling of the data layer, no built-in replication or high availability.
- **Mitigation**: Production runs on a single OCI instance with scheduled backups to `10.20.173.120`; restore drill tested in isolation before operational go/no-go.

## Alternatives Considered
- **PostgreSQL**: Rejected due to operational overhead of a separate database server on the OCI instance and complexity of backup/restore coordination.
- **MySQL/MariaDB**: Rejected for same reasons as PostgreSQL.

## Review
Review before any production scaling beyond a single instance or if concurrent write volume exceeds SQLite's capacity.
