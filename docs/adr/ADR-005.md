# ADR-005: No JWT/OIDC Authentication in This Release

## Status
Accepted

## Date
2026-11-07

## Context
The Aviation DMS requires user authentication and role-based access control. The production deployment requires secure session management, but implementing a full OIDC provider or JWT issuer would add significant complexity (issuer discovery, key rotation, token revocation, PKCE flows).

## Decision
Use opaque, server-managed HTTP-only session cookies (`__Host-kfl_session` + `__Host-kfl_csrf` CSRF pair) with:
- Session cookies: HTTP-only, SameSite=Strict, Secure in production
- CSRF double-submit token required on all state-changing requests
- Origin allow-listing via `CORS_ORIGINS` environment variable
- Session expiry: sliding `SESSION_TTL_SECONDS` (default 8 hours) capped by `SESSION_ABSOLUTE_MAX_SECONDS` (default 24 hours)
- Sessions revoked on logout, role change, and user role assignment changes
- Failed attempt rate limiting: 5 failures per 15-minute window → 15-minute lockout
- Development mode (`DEV_MODE=true`) uses identity headers (`X-Role`, `X-Actor`) — disabled in production
- JWT/OIDC is explicitly **not implemented**; these unused settings are not configured or advertised

## Rationale
- **Simplicity**: Session cookies are well-understood, easy to revoke server-side, and do not require token issuance infrastructure.
- **Server-side revocation**: Sessions are stored in the database and can be invalidated immediately (unlike stateless JWTs).
- **CSRF protection**: Double-submit cookie pattern protects against cross-site request forgery.
- **Reduced attack surface**: No OIDC provider to configure, no signing keys to rotate, no token storage on the client.
- **Aviation compliance**: Session-based audit trail with explicit actor attribution is easier to reconcile with controlled-document access requirements.

## Consequences
- **Positive**: Simple revocation, no key management, CSRF protection, server-controlled session lifecycle.
- **Negative**: Sessions are tied to a single server instance (no shared session store), no OAuth/OIDC federation, clients must support cookies.
- **Mitigation**: Single-instance deployment means no shared session store is needed; cookie-only clients are standard for browser-based applications.

## Alternatives Considered
- **JWT/Bearer tokens**: Rejected — stateless tokens are harder to revoke and require key rotation infrastructure.
- **OIDC provider (Keycloak/Auth0)**: Rejected — operational overhead, external dependency, configuration complexity not justified for the current scope.
- **Development identity headers in production**: Explicitly disabled; `DEV_MODE` header fallback is local-dev only.

## Review
Review before adding multi-instance deployment, mobile clients, or third-party identity federation.
