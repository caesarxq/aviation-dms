# ADR-006: Port Assignments for Staging and Production

## Status
Accepted

## Date
2026-11-12

## Context
Staging and production instances both run Docker Compose with backend (port 8000) and frontend (port 8080) services. The staging instance experienced persistent port conflicts (dead `docker-proxy` processes holding ports 8000/8080 after container removal), requiring Docker service restarts. Production runs on a private OCI instance with no port conflicts.

## Decision
- **Staging** (`10.20.4.234`): Backend bound to `0.0.0.0:8001`, frontend bound to `0.0.0.0:8081`. Ports are published but only reachable via the bastion Caddy proxy (no direct public access).
- **Production** (`10.20.1.69`): Backend bound to `0.0.0.0:8000`, frontend bound to `0.0.0.0:8080`. Ports are published but the backend is not directly reachable from the public internet (Caddy on bastion proxies to `10.20.1.69:8000/8080`).
- **Bastion** (`145.241.152.126`): Caddy listens on 443 for `roc.kfl.ke` and `stage.kfl.ke`; reverse-proxies to the respective backend/frontend ports.

## Rationale
- **Staging port isolation**: Changing staging ports avoids conflicts with leftover `docker-proxy` processes and keeps staging traffic localhost-only on the staging host.
- **Production standard ports**: Production uses 8000/8080 for consistency with application defaults; Caddy handles external HTTPS on 443.
- **Localhost binding**: Staging backend and frontend bind to `127.0.0.1` only, preventing external access to staging APIs directly.
- **Caddy as single entry point**: All external traffic flows through Caddy on the bastion, which handles TLS and routing to the correct backend.

## Consequences
- **Positive**: No port conflicts on staging, production uses standard ports, Caddy centralizes external access.
- **Negative**: Staging port changes require updates to `docker-compose.staging.yml`, `Caddyfile.bastion`, and any client configurations referencing staging ports.
- **Mitigation**: All port mappings are documented in deployment scripts and Caddyfile.bastion; staging is not directly accessible from outside the bastion.

## Alternatives Considered
- **Same ports on both instances**: Rejected — staging port conflicts caused repeated deployment failures.
- **Host networking**: Rejected — bridge networking with port mapping provides better isolation.

## Review
Review if staging is moved to a dedicated host without port conflicts, in which case standard ports (8000/8080) could be restored.
