# ADR-004: Isolated Upload-Validator Container

## Status
Accepted

## Date
2026-11-11

## Context
File uploads (personnel credentials, KCAA approval evidence, P3 audit evidence) must be scanned for malware and validated before persistence. The upload processing must be isolated from the main backend and must not have direct access to the DMS database or unrestricted document storage.

## Decision
Run `upload-validator` as a separate Docker container with:
- Image: `kfl-aviation-dms-backend:<tag>` (same image as backend, different command)
- User: `10002:10002`
- Read-only root filesystem
- `cap_drop: ["ALL"]`, `security_opt: ["no-new-privileges:true"]`
- `pids_limit: 32`, `mem_limit: 768m`, `cpus: 1.0`
- `tmpfs: ["/tmp:rw,noexec,nosuid,nodev,size=16m"]`
- Network: isolated `upload_validator` network (internal, no host port)
- Command: `uvicorn app.upload_validation_service:app --host 0.0.0.0 --port 9100`
- Backend connects via `DMS_UPLOAD_VALIDATOR_URL=http://upload-validator:9100/validate`
- 7-second total deadline for validation requests

## Rationale
- **Defense in depth**: Upload processing is isolated from the backend; a compromise of the validator does not expose the DMS database or document storage.
- **No direct DB access**: The validator service has no database volume or Docker secrets; it only validates and returns results.
- **Resource bounds**: Memory, CPU, and PID limits prevent resource exhaustion attacks.
- **Read-only root**: Prevents persistent modification of the validator filesystem.
- **Fail-closed**: Missing or unreachable validator causes uploads to return HTTP 503; uploads are never accepted without validation.

## Consequences
- **Positive**: Strong isolation, resource bounds, fail-closed behavior, no host port exposure.
- **Negative**: Additional container to manage, network latency for validation calls, asynchronous client complexity.
- **Mitigation**: Health checks on the validator; deployment scripts verify validator health before backend startup.

## Alternatives Considered
- **In-process validation**: Rejected — would give the validator direct access to the backend's memory and database context.
- **Sidecar pattern**: Rejected — separate container with isolated network provides stronger boundaries.
- **Cloud scanning API**: Rejected — would require sending document content outside the OCI/VPC boundary.

## Review
Review if validation throughput becomes a bottleneck or if additional file types require different validators.
