# ADR-002: Separate Staging and Production Environments

## Status
Accepted (revised 2026-11-18)

## Date
2026-11-12 (revised 2026-11-18)

## Context
The Aviation DMS requires two environments: a staging environment for testing and validation, and a production environment for operational use. Initially, production containers were deployed on the bastion host, which was incorrect. The production environment must be on a dedicated instance with strict security controls.

Staging and bastion share a single VM (`roc-dis`, `145.241.152.126`). Caddy runs on the bastion as TLS termination and reverse-proxies to the local staging backend on `127.0.0.1:8000` and frontend on `127.0.0.1:80`.

## Decision
- **Staging**: Shared bastion/staging VM `roc-dis` (`145.241.152.126`), dev mode (`DEV_MODE=true`), 1 GB storage quota, backend bound to `127.0.0.1:8000`, frontend bound to `127.0.0.1:80`. Accessible only through bastion Caddy on port 443.
- **Production**: Dedicated OCI instance `10.20.1.69` (Ubuntu 26.04 aarch64), strict security (`DEV_MODE=false`), 30 GB storage quota, ports 8000/8080, HTTPS via bastion Caddy reverse proxy.
- Independent `dms_data` volumes for each environment; volumes are never shared.
- Bastion `145.241.152.126` runs Caddy as TLS termination for `roc.kfl.ke` → production proxy and `stage.kfl.ke` → staging local backend.
- SSH on the shared VM is restricted to the operator's current IP allowlist only.

## Rationale
- **Security isolation**: Production handles operational records, KCAA evidence, and personnel credentials; staging uses test data. Separate instances prevent accidental cross-environment data exposure.
- **Quota differentiation**: Staging limited to 1 GB to prevent unbounded test data growth; production approved for 30 GB by the Records Custodian.
- **Configuration separation**: Production uses `DMS_TRUSTED_FRONTEND_IP=145.241.152.126/32` (bastion IP), HTTPS-only cookies, CSRF, and origin allow-listing; staging uses dev-mode identity headers.
- **Fail-closed deployment**: Production promotion requires manual approval gate; staging deploys via self-hosted GitHub Actions runner on the shared VM (no inbound SSH from GitHub Actions required).
- **Shared VM constraint**: Staging and bastion are the same host, so staging is reachable only through Caddy (localhost binding). SSH access is restricted to a single-IP allowlist.

## Consequences
- **Positive**: Clear environment boundaries, production security controls, no test data in production, independent backup/restore per environment, reduced SSH attack surface.
- **Negative**: Two instances to maintain, bastion dependency for production HTTPS, shared VM means staging and bastion share resources.
- **Mitigation**: Deployment scripts (`deploy-staging.sh`, `deploy-prod.sh`, `promote-to-production.sh`) automate environment-specific deployment; Caddy on bastion handles TLS termination; SSH restricted to operator IP allowlist.

## Alternatives Considered
- **Single instance with namespaces**: Rejected due to insufficient security isolation for aviation compliance records.
- **Terraform-provisioned OCI instance**: Terraform files removed; production instance created manually and managed directly via bastion.
- **Separate dedicated staging instance**: Rejected — shared bastion/staging VM avoids maintaining a second cloud instance; staging is internal-only via Caddy.

## Review
Review if additional environments (e.g., UAT, disaster recovery) are required or if staging should move to a dedicated host.
